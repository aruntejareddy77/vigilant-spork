# Plan 01-03: Startup Attestation & Deliverable Lineage Packaging

## Objective

Implement the cryptographic supply chain attestation engine and deliverable lineage subsystem for the Sovereign AI Workbench. Build an Ed25519-signed manifest verifier (`attestation_manifest.json`) supporting two-tier integrity checks (full byte-by-byte SHA-256 for install/first-boot, 64MB sparse head/tail chunk hashing for warm restarts) with strict fail-closed enforcement. Build a W3C PROV-O inspired lineage engine packaging sidecar manifests (`<filename>.lineage.json`) and injecting native provenance properties into Microsoft Office (.docx, .xlsx, .pptx), PNG images, and scripts, complete with bidirectional CLI verification (`sovereign lineage verify` & `sovereign lineage trace`).

## User Story Framing

**As an** industrial operator or plant engineer,  
**I want** mathematical assurance that local model weights and software binaries have not been altered or backdoored, and I want every generated engineering deliverable to carry unbreakable cryptographic links to its source documents, citations, and models,  
**So that** all generated outputs are fully defendable in regulatory audits and false deliverables can be conclusively identified.

<threat_model>
### ASVS & STRIDE Threat Modeling

- **OWASP ASVS Category:** V10.3 (Application Integrity), V8.1 (General Data Protection).
- **Threat T-01-06 (STRIDE: Elevation of Privilege / Tampering):** An attacker or corrupted update injects modified model weights, compromised binaries, or backdoored configuration files into the air-gapped system to skew decisions or execute unauthorized code.
  - *Mitigation:* Assets are cataloged in `attestation_manifest.json` signed offline with Ed25519. Startup runs two-tier verification (full SHA-256 or 64MB sparse chunk). Any mismatch halts startup immediately (exit code 1) and writes a tamper alert to the audit ledger. Fallback requires explicit `--dev-mode` or `--mock-models`.
- **Threat T-01-03 (STRIDE: Repudiation):** A user or operator denies generating an official calculation sheet, or disputes which model, tool, or document version was used to produce a deliverable.
  - *Mitigation:* W3C PROV-O inspired metadata schema binds deliverable SHA-256, model weights SHA-256, source document IDs with bounding-box citations, and exact audit ledger sequence span (`audit_start_seq`..`audit_end_seq`, `audit_tip_hash`). Stored in `<file>.lineage.json` and embedded into Office OOXML properties, PNG chunks, and script docstrings.
</threat_model>

## Multi-Source Coverage Audit

- **Requirements Covered:**
  - `SOVG-05`: Startup verification enforces checksum/attestation matching for model files and core binaries, failing closed on discrepancy.
  - `SOVG-06`: Every deliverable carries metadata linking its content to specific models, tools, and source documents used.
- **Locked Decisions Implemented:**
  - `D-09`: Signed JSON Manifest with SHA-256 Hashes & Ed25519 Signature (`attestation_manifest.json`).
  - `D-10`: Strict Fail-Closed in Production with Explicit `--dev-mode` / `--mock-models` Bypass.
  - `D-11`: Two-Tier Verification: Full SHA-256 on Install/First Boot + Inode/Stat Guard with Sparse 64MB Chunk Hashing on Warm Restarts.
  - `D-12`: Built-in Workbench CLI Commands (`sovereign attest generate / verify / sign`).
  - `D-13`: Dual Packaging: Sidecar JSON Manifest (`<filename>.lineage.json`) + Embedded Office Custom Properties (`.docx`, `.xlsx`, `.pptx`).
  - `D-14`: Comprehensive Auditable Lineage Schema (W3C PROV-O inspired).
  - `D-15`: Bidirectional Lineage CLI (`sovereign lineage verify <file>` & `sovereign lineage trace <file>`).
  - `D-16`: Uniform Sidecar Manifest + Format-Native Comment/Header Injections (`.py`/`.sh` headers, `.png` tEXt chunks).
